# DEW2019 aqueous fluid model ("fluid_DEW") — implementation strategy & progress

Status doc for porting the Deep Earth Water (DEW2019) aqueous species model into
MAGEMin's C engine, as a new solution phase `fluid_DEW`, sitting alongside the
other TC-group solution phases (`src/TC_database/`).

Source of truth for the physics + the target coupling design: `../MAGEMin.jl`
(Julia prototype). This doc records what exists on both sides, the architecture
decision this requires, the phased task list, and open questions.

---

## 0. Key finding: this is NOT a drop-in copy of the existing `aq17` phase

MAGEMin C already has one aqueous-fluid solution phase, `aq17` (Miron et al.
2017 dataset), fully wired through the **standard SS pipeline**:

- `TC_gem_function.c::G_FS_function` — per-species standard-state Gibbs energy
  (classic revised-HKF, fixed θ=228, ψ=2600)
- `tc_gss_function.c::G_SS_aq17_function` — builds the phase's endmember list/gbase
- `objective_functions.c::obj_aq17` / `px_aq17` / `p2x_aq17` — ideal+DH mixing,
  evaluated like any other solution-phase objective function
- `NLopt_opt_function.c::NLopt_opt_aq17_function` — local refinement via NLopt
- `objective_functions.c::DebyeHuckel` / `OsmoticCoeff` — extended (b-dot)
  Debye-Hückel activity + osmotic coefficient, already P-T dependent
- Dielectric constant + water density already ported:
  `TC_gem_function.c::rho_wat_calc` (HGK/Wagner-Pruss water EOS),
  `propSolvent_JN91_calc` (Johnson & Norton 1991), `propSolvent_SV14_calc`
  (Sverjensky et al. 2014 / "DM"), `propSolvent_FE97_calc`.

**So aq17 is generated as pseudocompounds and locally refined with NLopt,
exactly like a solid solution.**

The Julia prototype's DEW workflow (`main_tmp_dew.jl`) does **not** do that for
DEW. After the system-wide LP levelling step produces the component chemical
potentials (`LP_data.Gamma_lp`), it calls `aq_min_iterative` (in
`local_optimizer.jl`), which:

- takes `Gamma_lp` (fixed input, not something it searches over),
- computes each species' molality directly from `exp(mu_exp/RT)` given the
  species' own standard-state Gibbs energy and its oxide/H+ reaction
  stoichiometry (`mu_comp`),
- iterates *only* the activity-coefficient / ionic-strength self-consistency
  (Debye-Hückel-type `gamma_e`, water activity, charge balance) to convergence,
- has no discretized composition grid and no NLopt call at all.

This is a fundamentally different, cheaper, and exact (no discretization error)
speciation approach — it is a **closed-form-per-iteration fixed-point solve**,
not a bounded local minimization over site fractions.

**Architecture decision (drives everything below) — RESOLVED with user input
2026-08-11:**

`fluid_DEW` reuses `aq17`'s exact registration slot mechanism: in
`TC_init_database.c`, `aq17` already sits in `metapelite_db`/`metapelite_aq_db`'s
`SS[]` array with `n_SS_PC = 1` and discretization step `1.0` — i.e. it is
already special-cased to a single "pseudocompound" slot, not a real grid. So
`fluid_DEW` gets its own `SS_list` entry the same way (`n_SS_PC = 1`), and no
new phase-registration mechanism is needed.

What *is* new: at that slot, instead of NLopt refining a pseudocompound,
`fluid_DEW`'s composition/G is produced by the ported `aq_min_iterative`
fixed-point solver, driven directly by `gv.gam_tot` (Gamma) — not by
`obj_*`/`NLopt_opt_*`. This only runs under the **legacy solver path**
(`gv.solver == 0`, confirmed at `MAGEMin.c:511` → calls `LP()` in
`PGE_function.c`), per the coupling decision in §5. `gv.solver == 1/2/3`
(PGE/LP-hybrid, LP-only, etc. — `MAGEMin.c:534/591/692`) are untouched for v1.
So the hook site is inside `LP()` (`PGE_function.c`), called once per
iteration after `gv.gam_tot` is updated for that iteration, gated on
`gv.SS_list` containing `"fluid_DEW"`.

## 1. Inventory: MAGEMin.jl (source of physics + target coupling)

| Piece | File | Role |
|---|---|---|

| `species_activity`/`water_activity`/`compute_G_AQ` | `src/DEW_19_a-x.jl` | **Dead code** — reference fields (`.sf`, `.idm`, `.gex`) don't exist on the current `AQ_act_` struct. Superseded by `aq_min_iterative`. Do not port these. |
| `local_optimizer_aq_` struct, `init_aqueous_minimizer` | `src/local_optimizer.jl` | Per-species scratch state for the iterative solver |
| `aq_min_iterative` | `src/local_optimizer.jl` | **The solver to port.** Fixed-point iteration: molality from `mu_exp`, ionic strength, Debye-Hückel `gamma_e` per charge, water Setschenow-type term, H⁺ correction from charge balance, repeat until `z_res` (charge residual) converges |
| `print_local_minimum_AQ` | `src/local_optimizer.jl` | Debug/reporting only, not required for the port |
| `build_aqueous_model` | `src/DEW_19_a-x.jl` | Assembles `AQ_data_` for the active species subset given current bulk/oxide set + water phase properties (ρ_w, G_w from the TC liquid/H2O phase) |
| `main_tmp_dew.jl` | `src/main_tmp_dew.jl` | End-to-end order of operations: build igneous SS set → LP levelling → parse DEW species → build aqueous model → init solver → `aq_min_iterative` once, using the already-converged `Gamma_lp` |

Notes:
- `AQ_sol.gbase[i]` used inside `aq_min_iterative` is **not** `gbase_supcrt`/`gbase_hsc`
  directly — check `DEW_19_gbase`'s return value wiring in `build_aqueous_model`
  (`AQ_ref.gb`) carefully; confirm which of `gbase_supcrt`/`gbase_hsc` is used and
  in which energy convention (J vs kJ, HSC vs SUPCRT zero-point) before porting,
  since MAGEMin C's internal convention must match (see `HSC_to_SUPCRT`/
  `SUPCRT_to_HSC` already used around `G_FS_function`/`obj_aq17` in the C code).
- `main_tmp_dew.jl` runs `aq_min_iterative` **once**, after LP levelling — i.e.
  the prototype doesn't yet demonstrate iterating this to convergence jointly
  with the rest of the PGE loop across multiple outer iterations. Confirm with
  the user whether the production coupling should re-run DEW speciation every
  PGE iteration (as Gamma updates) or only after Gamma has converged.

## 2. Inventory: MAGEMin_v2.0.0 (target C engine)

Reusable as-is:
- `TC_gem_function.c::rho_wat_calc` — water density (HGK/Wagner-Pruss), input to everything downstream
- `TC_gem_function.c::propSolvent_JN91_calc`, `propSolvent_SV14_calc` — the two dielectric models DEW blends
- `TC_gem_function.c::G_FS_function` — near-identical HKF skeleton to `DEW_19_gbase`; **not** reusable directly (fixed θ=228, no c1/c2 generalization, no per-species ω₀ handling, no `element_formula`→oxide-basis conversion, no H⁺/H₂=0 special case) but the best template for the new `G_DEW_function`
- `objective_functions.c::DebyeHuckel`, `OsmoticCoeff` — A/B Debye-Hückel formulas match `Agamma`/`Bgamma` exactly (same constants: `1.824829238e6`, `50.29158649`); their b-dot/azero terms are Miron-2017-specific (GEMS parameterization) and differ from `aq_min_iterative`'s simplified fixed `a=3.72`, `b=0.03` Truesdell-Jones form — **do not reuse `DebyeHuckel`/`OsmoticCoeff` wholesale**, port `aq_min_iterative`'s own simpler formulas so behavior matches the Julia solver exactly
- `gv.gam_tot` / LP `Gamma` bookkeeping in `PGE_function.c` — C analogue of `LP_data.Gamma_lp`
- `gv.research_group`, `gv.EM_database` gating (`--rg`, `--db`) — precedent for how a new phase/dataset is scoped and selected on the CLI

Needs to be built new:
- DEW species parameter database in C (229 species: `T_r,P_r,G_ref,S_ref,a1..a4,c1,c2,Psi,eta,rH,omega0,theta,z,element_formula,mu_formula`) — mirror `TC_endmembers.c/.h` + `hash_init.h` + `Access_*_DB`/`find_*_id` pattern already used for `EM_db`/`FS_db`
- `G_DEW_function` in `TC_gem_function.c` — full port of `DEW_19_gbase`, including `gSolvent`/`psat`, `epsilon`/`smooth`, `born_B`
- Effective ionic radius table (`get_effective_radius` port) — small static lookup, straightforward
- New aqueous solver source (new file, e.g. `TC_database/DEW_aq_solver.c/.h`) — port of `local_optimizer_aq_` + `aq_min_iterative`
- Phase registration for `fluid_DEW`: add an `SS_list` entry (mirroring `aq17`'s `n_SS_PC = 1` slot, see §0 — resolved) to `metapelite_db` in `TC_init_database.c` first
- A branch in `LP()` (`PGE_function.c`) that, when `"fluid_DEW"` is in `gv.SS_list` and `gv.solver == 0`, calls the new solver instead of the standard `obj_*`/`NLopt_opt_*` path for that phase's slot (see §0)
- Species activation filtering (subset-of-active-oxides check, mirroring
  `get_species_params`'s `active` flag) — relates to existing reduced-system
  fragility noted in memory (`[[gh_reduced_system_support]]`); needs the same
  "tested, not assumed" caution for oxides at exactly 0

- [x] **Verification:** independently re-transcribed `aq_min_iterative` + `build_aqueous_model` into a standalone Python script (`dew_solver_reference.py`, self-contained, not importing the Phase 2 script or any C-derived data) and compared full convergence output (`gamma_e[5]`, `mu_Hp`, `a_coef`, `G`, and per-species `m1`/`mu`/`a`/`x` including the water row) against the compiled C solver for an 8-species system (5 exactly-self-consistent neutral anchors + Ca²⁺/OH⁻/H⁺ to exercise the charge-balance terms) run to convergence (16 iterations). All matched to 10 significant figures

This is a preview of a real risk for Phase 5/6: a naively-initialized or poorly-converged outer LP/PGE Gamma could make `fluid_DEW`'s inner solve diverge for the same reason — worth keeping in mind when designing the PGE hook's initial-guess strategy

### Phase 5 — PGE integration ✅ DONE 2026-08-11, runs end-to-end in a real MAGEMin calculation
- [x] Coupling decision confirmed: `fluid_DEW` speciation re-runs every `ss_min_LP` call (every LP outer iteration), only under the legacy solver (`gv.solver == 0` → `LP()` in `PGE_function.c`)
- [x] **Architecture landed differently than originally planned, in a better way:** rather than a special-cased branch inside `LP()`/`ss_min_LP`, `fluid_DEW` plugs into the *exact same* per-phase dispatch tables every other solution phase uses (`SS_init[]`, `SS_objective[]`/`P2X_read[]`/`PC_read[]`, `NLopt_opt[]`) — `NLopt_opt_fluid_DEW_function` is registered in the `NLopt_opt[]` slot and simply calls `DEW_aq_min_iterative` instead of `nlopt_optimize`. This means none of `ss_min_LP`/`copy_to_Ppc`/`PC_function`/`SS_UPDATE_function`/`run_LP` needed to change at all - they treat `fluid_DEW` as just another phase with an unusual solver inside its dispatch slot
- [x] Traced `copy_to_Ppc`'s contract in detail: it unconditionally *re-invokes* the phase's objective function (`SS_objective[ph_id]`) to get the unrotated G/μ for the LP pseudocompound pool, so a full bypass of the objective-function machinery wasn't possible - `obj_fluid_DEW`/`px_fluid_DEW`/`p2x_fluid_DEW` were written to satisfy that contract, backed by a new `DEW_aq_evaluate` (one-pass, non-iterating re-evaluation of the converged state, see `DEW_aq_solver.c`)
- [x] New `SS_ref.mu_comp` field (shared struct, `MAGEMin.h`) - allocated only for `fluid_DEW` (`initialize.c`), freed only for it (`MAGEMin.c`) - since no other phase needs a species' formation-reaction stoichiometry, only its composition
- [x] `struct ss_pc.xeos_pc[]` bumped from a hardcoded 25 to 130 (`MAGEMin.h`) - `fluid_DEW` can need far more x-eos slots (up to `DEW_N_SPECIES_DB=120` + water) for its single starting pseudocompound than any previous phase; existing tables are unaffected (C zero-fills unspecified trailing elements)
- [x] New `G_SS_fluid_DEW_init_function` (`tc_gss_init_function.c`) computes the active-species count once (from `gv.ox[]`, independent of any specific point) to fix `n_em`/`n_xeos`/`n_sf` for the whole run - unlike aq17's hardcoded 25, this varies by database/oxide-set
- [x] New `G_SS_fluid_DEW_function` (`tc_gss_function.c`) reuses `init_DEW_aqueous_model_at_point` (Phases 2-4, unmodified) to build each point's gbase/mu_comp/density; deactivates the phase when bulk H₂O is exactly 0, matching every other H₂O-dependent phase's convention
- [x] New pseudocompound seed (`SS_xeos_PC_mp.c`, `SS_mp_pc_init_function` - now takes `gv` as an added parameter, one new call site in `simplex_levelling.c`) - mostly-water-trace-species starting guess, computed at runtime (not a static compile-time table like every other phase's, since `fluid_DEW`'s species count isn't compile-time-fixed)
- [x] **Two real bugs found and fixed via an actual test run, not just by code review:**
  1. `SS_UPDATE_function`'s `xi_em[i]=exp(-mu[i]/RT)` needs `mu[]` to be hyperplane-relative (small numbers) - `NLopt_opt_fluid_DEW_function`'s solve correctly uses *absolute* gbase/`gv.gam_tot` (matching `aq_min_iterative.jl`), which left `mu[]` on the wrong basis for this specific downstream consumer. Fixed by calling `obj_fluid_DEW` (which now reads the rotated `gb_lvl`) right after the solve to populate `mu[]`/`df` correctly, mirroring exactly how every other phase's objective function is consulted for this purpose
  2. **User-caught:** `obj_fluid_DEW` hardcoded `d->gbase` (absolute) instead of `d->gb_lvl` (rotated/relative) - breaking the universal convention every `obj_*` in this codebase follows (the *caller* toggles `gb_lvl` between rotated and unrotated via `rotate_hyperplane`/`non_rot_hyperplane`; the objective function just reads whichever is current). This made `delta_G` report the phase's absolute G (~-365 kJ) instead of ~0 at equilibrium, and poisoned `sum_xi` into an astronomical garbage value (`exp` of a ~124x-too-large exponent). Fixed by reading `d->gb_lvl` uniformly, like `obj_aq17` does
